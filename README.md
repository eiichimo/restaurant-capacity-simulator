# 飲食店 売上キャパシティ・シミュレーター

飲食店の座席構成、時間帯別の来店頻度、厨房能力、提供・食事時間、客単価などから、1日の売上期待値と処理能力をモンテカルロ法で試算するWebアプリです。すべての計算・設定保存はブラウザ内で完結し、バックエンドや外部APIへデータを送信しません。

> 本アプリの結果は、入力した仮定に基づく確率的な試算です。実際の売上、利益、来店数、経営成果を保証するものではありません。

## 主な機能

- 時間帯ごとのポアソン到着（指数分布による到着間隔）
- 通常卓、1人専用カウンター、連続カウンターの時系列割り当て
- 1人分を1ジョブとする厨房キューと複数調理スロット
- 通常需要と、1分ごとに来店する飽和需要の2種類のシミュレーション
- 100 / 1,000 / 5,000 / 10,000営業日の反復試行
- シード付き疑似乱数 `mulberry32` による結果の再現
- 売上分布、売上指標、離脱理由、稼働率のグラフとテキスト表示
- ボトルネックの簡易判定
- 結果に基づくルールベースの運営改善仮説と比較試算案
- 入力・結果・制約をまとめたChatGPT解析用Markdownのコピー
- 設定の自動保存、プリセット、JSON入出力、結果CSV出力
- 数値欄の自由入力と、よく使う値を選べるモバイル対応の候補ドロップダウン
- Web Workerによるバックグラウンド計算
- レスポンシブ表示とキーボード操作

プリセットは「小規模ランチ店」「カウンター中心店」「4人卓中心店」の3種類です。いずれも計算例であり、特定業態の標準値ではありません。

## シミュレーションモデル

### 時刻

入力は `HH:mm`、内部計算は開店を0分とする分単位です。ラストオーダーは来店時刻ではなく、`来店時刻 + 注文確定までの平均時間` がラストオーダー以前かで判定します。受け付け済みの調理、食事、会計、片付けはラストオーダー後も継続します。

### 通常需要

各時間帯の平均来店組数を λ（組/分）とし、到着間隔を `-ln(1-U) / λ` で生成します。`U` はシード付き疑似乱数の `[0, 1)` の値です。グループ人数比率は合計が100でなくても合計1へ正規化し、重み付き抽選します。すべて0は入力エラーです。

### 座席の割り当て

座席形式ごとに次の資源を生成します。

- **通常卓**: 「1卓あたりの定員 × 卓数」。1グループが1卓を占有し、相席しない
- **1人専用カウンター**: 「席数」分の独立席。1人グループだけを案内する
- **連続カウンター**: 「1列あたりの席数 × カウンター列数」。同じ列内でグループ人数分の連続空席を確保する

連続カウンターは各席を順序付きの席スロットとして時系列管理します。空席の合計が足りても連続していなければ案内せず、別のカウンター列をまたいだ割り当てもしません。割り当てた席はグループの片付け完了時に同時解放します。

通常卓とカウンターの両方を利用できる場合は、割り当てによる未使用席数が少ない候補を優先し、同条件では設定順を使用します。

1. 最大卓定員・最大カウンター列席数のどちらもグループ人数を収容できない場合は定員超過離脱
2. 収容可能な卓または連続空席がその時刻にない場合は満席離脱
3. 着席後、注文確定がラストオーダーを超える場合はLO超過離脱
4. 注文を受け付けた場合、注文待ちから片付け完了まで卓または席スロットを占有

LO超過グループは、注文不可と分かる注文確定時刻まで卓を占有して離脱する、というMVP上の前提を採用しています。

### 厨房と食事

各客の料理を1ジョブとして、注文確定時点で厨房キューへ入れます。各ジョブは最も早く空く調理スロットへ順番に割り当て、`max(注文確定時刻, スロット空き時刻)` から調理します。調理完了を提供時刻とします。

- 「全員分が揃ってから食べ始める」有効: 全員が最後の料理の提供時刻から食事開始
- 無効: 各客が自分の料理の提供時刻から食事開始
- 最後の客の食事終了 + 会計時間 + 片付け時間で卓を解放

通常需要では、調理時間・食事時間・客単価を `平均 ± 変動幅` の一様分布で生成します。時間と客単価は0未満にならないよう補正します。

### 飽和需要

開店からラストオーダーまで1分ごとに1グループが来店します。グループ人数のみ通常設定の分布から抽選し、客単価・調理時間・食事時間は平均値に固定します。通常需要とは別のシード系列で、選択した試行回数だけ反復します。

`飽和需要の平均受け入れ人数 × 平均客単価` を「シミュレーション上の売上キャパシティ」とします。これは指定条件下での処理能力試算であり、数学的に保証された絶対上限ではありません。

## 入力値

| 区分 | 入力 | 意味 |
|---|---|---|
| 営業 | 開店 / ラストオーダー | 同一営業日内の受付時間 |
| 営業 | 注文確定時間 | 着席から料理ジョブ投入までの固定平均時間 |
| 営業 | 会計 / 片付け時間 | 完食後から卓解放までに加える時間 |
| 座席 | 座席形式 | 通常卓、1人専用カウンター、連続カウンターから選択 |
| 座席 | 定員・席数・列数 | 通常卓は定員×卓数、独立カウンターは席数、連続カウンターは1列席数×列数 |
| 来店 | 時間帯 / 組数 | 重複しない時間帯ごとの1時間あたり平均来店組数 |
| 来店 | 1〜6人比率 | グループ人数の相対的な発生重み |
| 厨房 | 同時調理可能人数 | 並列に稼働できる調理スロット数 |
| 厨房 | 平均調理時間 / 変動幅 | 1人分の調理所要時間 |
| 厨房 | 食事時間平均 / 変動幅 | 提供後の食事所要時間 |
| 厨房 | 全員分を待つ | 食事開始を最後の提供まで揃えるか |
| 客単価 | 平均 / 変動幅 | 各客の売上を生成する範囲 |
| 設定 | シード | 疑似乱数系列を決める整数 |
| 設定 | 試行回数 | 通常・飽和の各モードで反復する営業日数 |

開店時刻を変更すると、来店条件の「時間帯1・開始」も同じ時刻へ自動変更します。時間帯2以降と各時間帯の終了時刻は変更しません。

来店時間帯は開店〜ラストオーダー内かつ相互に重複しないものとします。空白時間帯は来店率0として扱います。

## 指標の計算方法

各営業日の指標は次のように計算します。

| 指標 | 定義 |
|---|---|
| 売上 | 受け入れた全客の客単価の合計（0円以上） |
| 来店組数 / 人数 | 生成された全グループ / 全人数 |
| 受け入れ組数 / 人数 | 注文を受け付けたグループ / 人数 |
| 離脱 | 満席、最大収容人数超過、LO超過ごとの組数・人数 |
| 売上機会損失 | 全離脱人数 × 平均客単価 |
| 提供待ち時間 | 注文確定から各料理の提供まで。平均は受入客単位 |
| 滞在時間 | 来店から卓解放まで。平均は受入グループ単位 |
| 客席リソース稼働率 | 通常卓は1卓を1単位、カウンターは1席を1単位とした占有分 ÷（全客席リソース単位 × 営業分） |
| 実席稼働率 | 開店〜LO内の `着席人数 × 卓占有分` ÷（総席数 × 営業分） |
| 厨房稼働率 | 開店〜LO内の全スロット調理分 ÷（スロット数 × 営業分） |
| 営業終了後処理 | `最後の卓解放時刻 - LO時刻`。0未満は0 |
| 最大厨房待ち | 注文確定済みかつ調理開始前のジョブが同時に最も多い数 |

客席リソース・実席・厨房の稼働率は数値誤差を含めて0〜100%に収めます。LO後の占有・調理は稼働率の分子と分母に含めません。通常卓は利用人数にかかわらず卓1単位を占有しますが、カウンターは実際に割り当てた席数分を占有します。このため、実席稼働率との差は主に通常卓の空席ロスを示します。

複数試行の平均、最小、最大に加え、売上の中央値・下位10%点・上位10%点は、並べ替えた標本上の位置を線形補間して求めます。キャパシティ消化率は `通常需要の平均売上 ÷ 売上キャパシティ` です。

## ボトルネック判定の閾値

閾値は `src/simulation/bottleneck.ts` の `BOTTLENECK_THRESHOLDS` に集約しています。

| 定数 | 値 | 用途 |
|---|---:|---|
| `lowUtilization` | 45% | 需要不足の低稼働判定 |
| `highTableUtilization` | 80% | 客席高稼働 |
| `highKitchenUtilization` | 80% | 厨房高稼働 |
| `seatingMismatchGap` | 20ポイント | 客席リソース稼働率と実席稼働率の乖離 |
| `longServiceWaitMinutes` | 20分 | 長い提供待ち |
| `manyRejectedGroups` | 2組/日 | 離脱が多い判定 |
| `lastOrderShare` | 15% | 全離脱に占めるLO超過割合 |

- **需要不足**: 客席リソース・厨房稼働率が45%未満、かつ平均離脱が2組未満
- **客席制約**: 客席リソース稼働率80%以上、または満席離脱が平均2組以上
- **座席構成の不一致**: 客席リソース稼働率が実席稼働率より20ポイント以上高く、満席離脱あり
- **厨房制約**: 厨房稼働率80%以上、または平均提供待ち20分以上
- **ラストオーダー設定**: LO超過が平均2組以上、または全離脱の15%以上
- **複合制約**: 客席制約と厨房制約の双方に該当

複数条件に当てはまる場合は複数の示唆を表示します。判定は原因を断定するものではありません。

## 運営改善候補とChatGPT用テキスト

結果画面では、検出された制約と集計値から、厨房スロット、調理時間、卓構成、片付け時間、ラストオーダー、時間帯別需要などを1項目ずつ変更する比較試算案を提示します。これはルールベースの改善仮説であり、実行を推奨・保証するものではありません。

「ChatGPT解析用テキストをコピー」では、次の情報をMarkdownへまとめます。

- 入力設定とシード・試行回数
- 通常需要・飽和需要の主要集計値
- ボトルネック判定とアプリ内の改善仮説
- モデルで扱っていない費用・顧客満足度などの注意事項
- 変更値、比較条件、副作用、追加収集データを尋ねる分析指示

コピーするまで情報はブラウザ外へ送信されません。店舗名や個人情報は自動で含めません。コピー後に外部サービスへ貼り付ける場合は、そのサービスのデータ取扱方針を確認してください。生成AIの回答も経営成果を保証するものではなく、実店舗の費用・法令・安全・品質を踏まえた人による判断が必要です。

## 設定データ

設定は変更のたびに `localStorage` へ自動保存されます。JSONには `schemaVersion: 2` を含め、読込時にオブジェクト構造、型、値、時刻範囲を検証します。不正なJSONは適用せず、日本語のエラーを表示します。旧 `schemaVersion: 1` は自動移行し、名称に「カウンター」を含む1人卓を1人専用カウンター、それ以外を通常卓として従来の割り当て結果を維持します。CSVは通常シミュレーションの各営業日を1行として出力します。

## モデル上の制約

- 通常卓の相席を扱わない
- 通常卓の連結を扱わない（連続カウンターだけは同じ列内の隣接席を利用する）
- 店内で席が空くまで待つ待ち行列を扱わない
- メニューごとの調理工程を扱わない
- スタッフ個人の作業能力を扱わない
- テイクアウトを扱わない
- 注文追加を扱わない
- 予約、キャンセル、季節性、天候を扱わない
- 来店客同士の時間的な相関を、時間帯別の独立したポアソン過程へ単純化している
- 調理スロットは料理以外の作業や段取り替えを扱わない
- 通常需要の各変動値は一様分布であり、実店舗の歪んだ分布や相関を表現しない
- 飽和需要結果は数学的な絶対上限ではない
